## 1. Frontend Routes (Hash-Based Virtual Router)

The entire experience lives on ONE Next.js route (`/`, file: `src/app/page.tsx`) driven by a hash router (`src/lib/router.ts`). Deep links and browser back/forward work.

| Hash | View component | Notes |
|---|---|---|
| `#/` | `components/home/home-view.tsx` | Hero + all marketing sections |
| `#/store` | `components/store/store-view.tsx` | All products + filters |
| `#/store/:slug` | same | Category world (slug = category slug) |
| `#/product/:slug` | `components/product/product-view.tsx` | Product details |
| `#/builds` | `components/builds/builds-view.tsx` | PC builds experience |
| `#/build/:slug` | `components/builds/build-view.tsx` | Build details |
| `#/maintenance` | `components/maintenance/maintenance-view.tsx` | Maintenance request form |
| `#/cart` | `components/cart/cart-view.tsx` | Full cart page |
| `#/checkout` | `components/cart/checkout-view.tsx` | Customer info → WhatsApp order |
| `#/admin` | `components/admin/admin-view.tsx` | Mock login → dashboard |
| `#/admin/:section` | same | `overview/products/categories/builds/orders/maintenance/settings` |

**Phase 02 option A (recommended):** keep the virtual router; replace repository internals with API calls.
**Option B:** migrate to real Next.js routes — the view components are self-contained and portable; the router is the only place that maps names → URLs.

## 2. Domain Entities (source of truth: `src/types/index.ts`)

- **Product** — id, slug, name, brand, shortDescription, description, price, oldPrice?, promotionalLabel?, categoryId, images[], availability (`in-stock|low-stock|out-of-stock|pre-order`), stockQty, featured, isNew, rating, specs[] (`{label, value}`), specLayout (`device|component|accessory`), createdAt
- **Category** — id, slug, name, tagline, description, image, accent (hex), icon (lucide name), order
- **PCBuild** — id, slug, title, type (`gaming|workstation|budget|creator`), description, images[], components[] (`{id, role, name, spec?, qty, price?}`), totalPrice, availability, performance[] (`{label, score 0-100}`), featured
- **CartItem** — productId, qty (client-only state)
- **OrderRecord** — id, ref, customerName, customerPhone, items[] (order lines), total, createdAt, status (`new|contacted|confirmed|completed|cancelled`), notes?
- **MaintenanceRecord** — id, ref, customerName, customerPhone, deviceType (`laptop|desktop|phone|other`), deviceBrand?, deviceModel?, problemCategory (`hardware|software|performance|os|display|other`), problemDescription, additionalNotes?, createdAt, status (`new|in-review|repairing|ready|delivered|cancelled`), adminNotes?
- **StoreSettings** — storeName, tagline, whatsappNumber (E.164 digits only), whatsappDisplay, facebookUrl, tiktokUrl, address, businessDescription, logoUrl?

Suggested Prisma models mirror these 1:1 (Category `order` for reordering; spec arrays become JSON fields or related Spec rows).

## 4. Repository Interfaces (the Phase-02 seam)

`src/lib/repositories.ts` exposes typed async repositories — **the only mutation path the UI uses**:

- `ProductRepository`: `list(filter?)`, `get(idOrSlug)`, `related(productId, limit?)`, `create(input)`, `update(id, patch)`, `remove(id)`
- `CategoryRepository`: `list()`, `get(idOrSlug)`, `create`, `update`, `remove`, `reorder(id, 'up'|'down')`
- `BuildRepository`: `list()`, `get(idOrSlug)`, `create`, `update`, `remove`
- `OrderRepository`: `list()`, `update(id, patch)`, `remove(id)`
- `MaintenanceRepository`: `list()`, `create(input)`, `update(id, patch)`, `remove(id)`
- `SettingsRepository`: `get()`, `update(patch)`

Current implementations wrap the zustand mock store with ~100–260 ms simulated latency (so the UI's pending/skeleton states are real). **Swap them with API-backed implementations** (fetch → `/api/*` route handlers) and no view needs to change. Reads currently bypass repos (reactive zustand selectors) — for Phase 02, either (a) keep a client cache hydrated by repos, or (b) introduce TanStack Query and point it at the same interfaces.

`ProductFilter` supports: `categoryId`, `search` (name/brand/descriptions), `minPrice`, `maxPrice`, `availability[]`, `sort` (`newest|price-asc|price-desc|featured`). Re-implement this exact semantics server-side.

## 7. WhatsApp Workflows (all message builders in `src/lib/whatsapp.ts`)

Number: **`201553153156`** (owner-supplied, centralized in `src/lib/config.ts` → `BUSINESS.whatsappNumber`; never hardcode elsewhere).

| Flow | Builder | Trigger |
|---|---|---|
| Cart order | `buildOrderMessage` / `orderWhatsAppUrl` | Checkout "افتح واتساب وأرسل" — also records order in mock DB |
| Single product inquiry | `buildProductMessage` / `productWhatsAppUrl` | Product page CTA |
| Build inquiry | `buildBuildMessage` / `buildWhatsAppUrl` | Build page CTA |
| Maintenance request | `buildMaintenanceMessage` / `maintenanceWhatsAppUrl` | Maintenance form confirm — also records request in mock DB |

All builders produce professional Arabic messages (products, quantities, prices, totals, customer info) and use `encodeURIComponent` on the `wa.me` text param.

**Honesty contract baked into the UI:** opening WhatsApp never displays a fake "order submitted/paid" success. Phase 02 should add real delivery confirmation (e.g., WhatsApp Business API) before changing that copy.

## 8. Image Upload Requirements (Phase 02)

- Admin currently accepts **image URLs** (textarea, one per line) with live previews — swap the textarea with a real upload widget (route → storage). Keep writing to the same `images: string[]` field.

## 11. Known Limitations (by design in Phase 01)

- No payment processing (WhatsApp-only commerce, per business model).
- No customer accounts/registration (by requirement).
- Admin "login" is a demo gate — zero real security.
- Cart/orders/settings persist in browser localStorage — demo persistence only, not a database.
- Ratings on products are sample data (no review system exists).
- The performance meters on builds are relative indicators labeled "تقدير نسبي للعرض".
- No real WhatsApp delivery/confirmation of messages.
- Analytics numbers in the admin overview are simulated (labeled).
